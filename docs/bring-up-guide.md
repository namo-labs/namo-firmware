# 파일럿 조립·검증 가이드

> 버전: v0.1 · 작성일: 2026-09-01
> 이 문서는 순서대로 따라 하는 절차서입니다. **각 Stage의 합격 기준을 통과하기 전에는 다음 Stage로 넘어가지 않습니다.**

## 읽기 전에

### 이 순서를 지켜야 하는 이유

전기와 물을 한꺼번에 연결해놓고 전원을 넣으면, 문제가 생겼을 때 원인이 배선인지 코드인지 부품 불량인지 구분할 수 없습니다. 아래 순서는 **한 번에 하나씩만 늘리도록** 짜여 있습니다.

특히 Stage 2를 건너뛰고 펌프부터 연결하는 것을 피해야 합니다. MOSFET이 제대로 안 켜지는 상태에서 펌프를 물리면 MOSFET이 뜨거워지고, 최악의 경우 켜진 채로 고장 나 펌프가 멈추지 않습니다.

### 안전 원칙

- **물과 전자부품은 항상 분리된 높이에 둡니다.** 브레드보드는 물통보다 높은 곳에, 가능하면 다른 테이블에 둡니다.
- **첫 급수 테스트는 화분이 아니라 양동이에서 합니다.**
- 배선을 바꿀 때는 반드시 12V 어댑터를 뽑습니다. USB만 뽑는 것으로는 부족합니다.
- 자리를 비울 때는 12V 어댑터를 뽑습니다. 파일럿이 안정되기 전까지는 무인 가동하지 않습니다.

### 준비물 (Stage 0 시작 전)

`shopping-list.md`의 필수 항목이 모두 있어야 합니다. 멀티미터는 Stage 1부터 필요합니다.

## Stage 0 — 개발환경과 첫 플래싱

**목표**: 맥에서 ESP32-S3로 Rust 코드를 올려 시리얼 로그를 확인합니다.

내장 LED는 보드마다 핀이 다르고 RGB(WS2812)인 경우도 많아, 이 단계에서는 판정 기준으로 쓰지 않습니다. 로그가 올라오면 툴체인·플래싱·시리얼이 모두 살아있다는 뜻이라 목적에는 충분합니다.

### 절차

0. **rustup이 있는지 먼저 확인합니다.**

```bash
which rustup
```

`rustup not found`가 나오면 여기서 멈추고 아래를 먼저 해결합니다. `espup`은 rustup 위에서만 동작하므로, Homebrew로 설치한 rust만 있으면 Xtensa 툴체인을 깔 수 없습니다.

```bash
# 현재 rust가 어디서 왔는지 확인
which -a cargo rustc
brew list --versions rust
```

`/opt/homebrew/bin/cargo`가 나오면 Homebrew rust입니다. 다음 순서로 교체합니다.

```bash
brew uninstall rust          # rustup과 PATH가 충돌하므로 먼저 제거
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh
source "$HOME/.cargo/env"
which -a cargo               # /Users/<이름>/.cargo/bin/cargo 가 먼저 나와야 합니다
```

Homebrew rust를 남겨두면 `/opt/homebrew/bin`이 PATH 앞에 있어 rustup 툴체인이 무시됩니다. 빌드가 되는데 타겟만 없다는 혼란스러운 상태가 됩니다.

`namo-core`는 Homebrew rust로도 테스트가 돌아가지만, 펌웨어 빌드부터는 rustup이 반드시 필요합니다.

1. Xtensa 툴체인을 설치합니다.

```bash
cargo install espup
espup install
# 설치 후 매 셸마다 필요. .zshrc에 넣어두면 편합니다.
. $HOME/export-esp.sh
```

2. 플래싱 도구와 프로젝트 생성기를 설치합니다.

```bash
cargo install cargo-espflash espflash ldproxy
cargo install cargo-generate
```

3. 보드를 USB로 연결하고 정체를 확인합니다.

```bash
espflash board-info
```

출력에서 `Chip type`, `Crystal frequency`, `Features`를 기록합니다. `Features`에 옥탈 PSRAM이 표시되면 `hardware-pilot-status.md`의 H2를 "옥탈"로 갱신하고, **GPIO33~37을 절대 쓰지 않습니다.**

4. 템플릿으로 시험 프로젝트를 만들고 빌드해봅니다. (이 프로젝트는 검증용이며 나중에 버립니다.)

```bash
cd /tmp
cargo generate esp-rs/esp-idf-template cargo
# MCU는 esp32s3 선택
```

5. **생성된 `.cargo/config.toml`의 `[env]`에 ESP-IDF 버전을 반드시 고정합니다.**

```toml
[env]
MCU = "esp32s3"
ESP_IDF_VERSION = "v5.4.4"
```

이걸 빠뜨리면 `esp-idf-sys`가 기본값인 **v5.2.3**을 받는데, 그 버전은 다음 오류로 빌드가 실패합니다.

```
CMake Error ... Failed to run Python dependency check. Error: 255
```

메시지는 "Python을 실행하지 못했다"고 말하지만 실제 원인은 다릅니다. 최신 pip가 패키지 배포명을 PEP 625 방식으로 정규화해 `ruamel.yaml`을 `ruamel-yaml`로 설치하는데, v5.2.3의 의존성 검사에는 이 이름 차이를 흡수하는 폴백이 없습니다. 패키지는 멀쩡히 설치돼 있는데도 "없다"고 판정하고, 그 실패가 종료코드 255로 나와 cmake가 엉뚱한 메시지를 출력합니다.

v5.4의 `get_version()`에는 정규화 폴백이 들어가 이 문제가 해결됐습니다. 재설치·다운그레이드로는 고쳐지지 않으니 **버전 고정이 유일한 해결책입니다.**

`.embuild` 디렉토리는 프로젝트마다 새로 생기므로, 새 크레이트를 만들 때마다 이 설정이 필요합니다.

첫 빌드는 ESP-IDF를 내려받느라 5~10분 걸립니다. 정상입니다.

### 합격 기준

- `which rustup`이 경로를 돌려줍니다.
- `which -a cargo`의 첫 줄이 `~/.cargo/bin/cargo`입니다.
- `espflash board-info`가 ESP32-S3를 인식합니다.
- 시험 프로젝트가 빌드되고 플래싱되며, `espflash monitor`에 로그가 올라옵니다.

> **통과 기록 (2026-09-03)** — 툴체인(rustup + Xtensa 1.97.0.0), 빌드(752KB), 플래싱(410KB, 파티션의 4.9%), 시리얼 로그까지 모두 확인했습니다. 보드 실측값은 `hardware-pilot-status.md` §3에 기록했습니다.

### 막히면

- `espup install`이 rustup을 못 찾는다고 하면 위 0번으로 돌아갑니다.
- 포트를 못 찾으면 `ls /dev/cu.*`로 확인합니다. `usbmodem` 또는 `usbserial`로 시작하는 이름입니다.
- 두 개가 보이면 하나는 USB-JTAG, 하나는 UART 브리지입니다. 둘 다 시도해봅니다.
- 인식이 안 되면 BOOT 버튼을 누른 채로 USB를 꽂고 놓습니다.
- 충전 전용 USB 케이블은 데이터선이 없어 포트 자체가 잡히지 않습니다. `ls /dev/cu.*`에 아무것도 늘지 않으면 케이블부터 바꿔봅니다.
- `espflash monitor`는 붙는 데 2초쯤 걸려서 부트로더 로그를 놓칩니다. 앱 로그만 보이고 부팅 메시지가 없어도 정상입니다. 부트 로그가 꼭 필요하면 `espflash flash --monitor`로 플래싱과 동시에 붙습니다.

## Stage 1 — 플로트 스위치 (물통 유무)

**목표**: 물통에 물이 있는지 없는지를 ESP32가 읽습니다.

물이 없을 때 펌프가 도는 것이 이 시스템에서 가장 흔한 고장 원인입니다. 수중 펌프는 공회전하면 금방 망가집니다. 그래서 펌프보다 이걸 먼저 만듭니다.

### 1-A. 멀티미터로 방향부터 확인 (ESP32 연결 전)

플로트 스위치는 부착 방향에 따라 논리가 반대가 됩니다. 코드를 쓰기 전에 실물로 확정합니다.

1. 멀티미터를 **도통(continuity) 모드**로 놓습니다. 보통 소리 표시(♪) 아이콘입니다.
2. 스위치의 두 선에 각각 프로브를 댑니다.
3. 플로트(떠 있는 부품)를 손으로 **위로 올린 상태**에서 소리가 나는지 기록합니다.
4. 플로트를 **아래로 내린 상태**에서 소리가 나는지 기록합니다.

| 플로트 위치 | 삐 소리 | 의미 |
|---|---|---|
| 위 (물 있음) | 남 | 물 있음 = 도통 |
| 위 (물 있음) | 안 남 | 물 있음 = 개방 |

두 상태의 결과가 같으면 스위치 불량입니다.

결과를 `hardware-pilot-status.md`의 H7에 적습니다. 코드의 논리를 여기에 맞춥니다.

### 1-B. 브레드보드 연결

```text
플로트 스위치 선 1 ── ESP32 GPIO5
플로트 스위치 선 2 ── ESP32 GND
```

내부 풀업을 켜므로 외부 저항은 필요 없습니다. 도통 시 GPIO5는 LOW, 개방 시 HIGH로 읽힙니다.

### 1-C. 물통 장착

L형 수평 플로트 스위치는 **물통 측면**에 다는 부품입니다. 나사산에 맞는 구멍을 뚫고 고무 패킹과 너트로 조입니다.

- 장착 높이가 곧 "물 없음" 판정 수위입니다. 펌프 흡입구보다 **위쪽**에 답니다. 그래야 물이 완전히 마르기 전에 경고가 뜹니다.
- 구멍 뚫기가 부담되면 이 단계를 미루고, 손으로 플로트를 올렸다 내리는 것으로 1-D를 먼저 통과해도 됩니다.

### 1-D. 코드로 읽기

물통에 물을 채웠다 비우면서 시리얼 로그를 봅니다.

### 합격 기준

- 플로트를 올리고 내릴 때 로그의 `reservoir` 값이 바뀝니다.
- 물을 채웠을 때 `ok`, 비웠을 때 `empty`로 나옵니다. **반대로 나오면 여기서 고칩니다.** 이걸 반대로 둔 채 다음으로 가면 빈 물통에서 펌프가 돕니다.
- 물통을 흔들어도 값이 초당 여러 번 튀지 않습니다 (디바운스 확인).

## Stage 2 — MOSFET 무부하 검증 (펌프 연결 전)

**목표**: GPIO4의 3.3V 신호로 AOD4184가 **완전히** 켜지는지 확인합니다.

⚠️ **이 Stage에서는 펌프를 연결하지 않습니다.** 부분도통 상태를 모르고 펌프를 물리면 MOSFET이 발열합니다.

### 2-A. 모듈 단자 파악

모듈의 실크스크린을 읽고 `hardware-pilot-status.md` H5에 적습니다. 보통 이렇게 생겼습니다.

- 굵은 나사 단자 2쌍: 한쪽은 전원 입력(`VIN+`/`VIN-` 또는 `DC+`/`DC-`), 다른 쪽은 부하 출력(`OUT+`/`OUT-`)
- 얇은 핀 2~3개: 트리거 입력 (`SIG`/`GND`, 또는 `PWM`/`GND`)

### 2-B. 배선 (펌프 자리는 비워둠)

```text
12V 어댑터 (+) ──── 모듈 VIN+
12V 어댑터 (−) ──── 모듈 VIN−
모듈 SIG        ──── ESP32 GPIO4
모듈 GND        ──── ESP32 GND
ESP32 GND       ──── 12V 어댑터 (−)      ★ 공통 접지
GPIO4           ──── 10kΩ ──── GND       ★ 풀다운
```

**OUT 단자에는 아무것도 연결하지 않습니다.**

### 2-C. 측정

1. 멀티미터를 **DC 전압 모드(20V 범위)** 로 놓습니다.
2. 검은 프로브를 `OUT−`, 빨간 프로브를 `OUT+`에 댑니다.
3. GPIO4를 LOW로 두고 측정합니다.
4. GPIO4를 HIGH로 두고 측정합니다.

| GPIO4 | OUT 양단 전압 | 판정 |
|---|---|---|
| LOW | 0V 근처 | 정상 (꺼짐) |
| HIGH | 11.5V 이상 | ✅ 정상 (완전히 켜짐) |
| HIGH | 5~10V | ❌ 부분도통. 3.3V로 부족함 |
| HIGH | 0V 근처 | ❌ 배선 오류 또는 단자 착각 |

### 합격 기준

- GPIO4 HIGH일 때 OUT 양단이 **11.5V 이상**입니다.

### 실패하면

- 먼저 공통 접지를 확인합니다. 이게 빠지면 거의 항상 안 켜집니다.
- 여전히 부분도통이면 3.3V 게이트 구동이 부족한 것입니다. 로직레벨 MOSFET 모듈을 추가로 사거나, ESP32의 5V 핀으로 구동하는 레벨시프터를 넣습니다. **이 상태로 펌프를 연결하지 않습니다.**

## Stage 3 — 펌프 첫 구동 (양동이)

**목표**: 실제로 물이 나옵니다.

⚠️ **화분에 하지 않습니다.** 양동이 두 개(물 담긴 것, 받는 것)로 합니다.

⚠️ **수중 펌프는 반드시 물에 잠긴 상태에서만 켭니다.** 공회전은 몇 초로도 손상을 줍니다.

### 3-A. 다이오드 장착

1N4007을 펌프 양단에 **역방향**으로 답니다.

```text
캐소드(몸통에 회색/검은 띠가 있는 쪽) ──── 펌프 (+) 쪽
애노드(띠 없는 쪽)                   ──── 펌프 (−) 쪽 (= 모듈 OUT−)
```

방향을 반대로 꽂으면 전원을 넣는 즉시 단락됩니다. 띠 위치를 두 번 확인합니다.

### 3-B. 배선 완성

Stage 2 배선에 펌프를 추가합니다.

```text
모듈 OUT+ ──── 펌프 (+)
모듈 OUT− ──── 펌프 (−)
```

### 3-C. 첫 구동

1. 펌프를 물이 담긴 양동이에 완전히 잠기게 넣습니다.
2. 튜브 끝을 빈 양동이에 넣습니다.
3. 12V를 연결합니다.
4. **2초만** 켜는 명령으로 시작합니다.

### 합격 기준

- 물이 나옵니다.
- 명령이 끝나면 **물이 즉시 멈춥니다.**
- MOSFET 모듈을 손으로 만져 미지근한 정도입니다. 뜨거우면 즉시 전원을 뽑고 Stage 2로 돌아갑니다.

### 사이펀 현상 확인 (중요)

펌프를 끈 뒤에도 물이 계속 나오면 사이펀입니다. 튜브가 물을 계속 빨아내 화분이 물바다가 됩니다.

- 원인: 튜브 토출구가 물통 수면보다 낮음
- 해결: 토출구를 **항상 물통 수면보다 높게** 배치합니다. 튜브 중간에 최고점을 만들어도 됩니다.

이 확인을 화분에서 하면 늦습니다. 양동이에서 반드시 봅니다.

## Stage 4 — 유량 캘리브레이션

**목표**: "펌프 1초 = 몇 mL"를 실측합니다.

카탈로그의 240L/h는 양정 0일 때 값이라 실제와 크게 다릅니다. 이 값이 틀리면 급수량이 전부 틀립니다.

### 절차

1. **실제 설치할 높이와 튜브 길이 그대로** 배치합니다. 이 조건이 바뀌면 다시 측정해야 합니다.
2. 계량컵을 토출구 아래에 둡니다.
3. 펌프를 정확히 10초 구동합니다.
4. 나온 물의 양을 mL로 읽습니다.
5. 3회 반복해 평균을 냅니다.

```text
ml_per_second = 평균 mL / 10
```

6. 결과를 `cfg.toml`의 `ml_per_second`에 넣습니다.

### 합격 기준

- 3회 측정값의 편차가 평균의 10% 이내입니다.
- 설정값을 넣은 뒤 "100mL 급수" 명령의 실제 토출량이 80~120mL 안에 들어옵니다.

### 참고

- 튜브 안에 물이 차 있는 상태와 비어 있는 상태의 첫 초 토출량이 다릅니다. 매번 같은 조건(튜브에 물이 찬 상태)에서 측정합니다.
- 첫 급수는 튜브를 채우느라 실제 토출이 적습니다. 이 오차는 파일럿에서 허용합니다.

## Stage 5 — HHCC BLE 수집

**목표**: 화분 센서의 네 값을 ESP32가 읽습니다.

### 절차

1. HHCC에 배터리(CR2032)를 넣고 흙에 꽂습니다. 마른 화분에 꽂아도 됩니다.
2. Flower Care 앱으로 한 번 페어링해 정상 동작을 확인합니다. 확인 후 앱은 꺼둡니다.
3. ESP32에서 BLE passive 스캔을 돌리고, 서비스 UUID `0xFE95` 광고를 로그로 봅니다.
4. MiBeacon 파싱을 붙여 값을 뽑습니다.

### 알아둘 것

- **한 광고 패킷에는 측정값이 하나만 들어옵니다.** 수분·온도·조도·전도도가 번갈아 오므로, 네 값이 모두 채워지려면 수 분이 걸립니다. 처음에 `null`이 섞여 보이는 것은 정상입니다.
- 측정 갱신 자체가 수 분 주기입니다. 물을 준 직후 수분 값이 바로 안 오릅니다.
- 배터리 잔량은 광고에 없을 수 있습니다. 이번 파일럿에서는 후순위입니다.

### 합격 기준

- 흙 수분·온도·조도·전도도 네 값이 모두 한 번씩 로그에 찍힙니다.
- 마른 흙에 물을 부으면 수분 값이 몇 분 안에 오릅니다.
- 손으로 센서를 가리면 조도 값이 떨어집니다.

## Stage 6 — WiFi와 MQTT

**목표**: 원격에서 상태를 보고 급수 명령을 보냅니다.

### 6-A. Mosquitto 실행 (맥)

```bash
docker run -d --name mosquitto -p 1883:1883 \
  -v "$PWD/gateway/mosquitto.conf:/mosquitto/config/mosquitto.conf" \
  eclipse-mosquitto
```

설정 파일은 레포의 `gateway/mosquitto.conf`입니다. 레포 루트에서 실행합니다.

파일럿은 LAN 안에서만 쓰므로 익명 접속을 허용합니다. **공유기 포트포워딩을 하지 않습니다.** 인증 없는 브로커가 인터넷에 열리면 누구나 펌프를 켤 수 있습니다.

### 6-B. 맥에서 구독 테스트

```bash
brew install mosquitto
mosquitto_sub -h localhost -t 'namo/#' -v
```

### 6-C. ESP32 연결

WiFi SSID·비밀번호와 브로커 IP를 `cfg.toml`에 넣습니다. 브로커 IP는 맥의 LAN IP입니다 (`ipconfig getifaddr en0`).

⚠️ ESP32는 **2.4GHz만** 지원합니다. 5GHz 전용 SSID에는 붙지 않습니다.

### 6-D. 급수 명령 보내기

```bash
mosquitto_pub -h localhost -t 'namo/pilot/<id>/water/cmd' \
  -m '{"id":"test-001","issued_at":'"$(date +%s)"',"ttl_s":15,"dose_ml":50}'
```

### 합격 기준

- 텔레메트리가 10초마다 올라옵니다.
- 명령을 보내면 물이 나오고 `water/result`에 `completed`가 옵니다.
- ESP32 전원을 뽑으면 `status`가 `offline`으로 바뀝니다 (LWT).
- **같은 `id`로 다시 보내면 물이 두 번 나오지 않습니다** (멱등성).
- `issued_at`을 1분 전으로 조작해 보내면 아무 일도 일어나지 않습니다 (TTL).

## Stage 7 — Zigbee 누수센서

**목표**: Aqara 누수센서 상태가 ESP32에 전달됩니다.

### macOS의 제약

Docker Desktop for Mac은 USB 장치를 컨테이너에 넘기지 못합니다. `--device /dev/tty...`가 리눅스처럼 동작하지 않습니다.

따라서 **Zigbee2MQTT는 Docker 없이 맥에 직접 설치해 실행합니다.**

```bash
brew install node
git clone --depth 1 https://github.com/Koenkk/zigbee2mqtt.git
cd zigbee2mqtt && npm ci
```

### 설정

`data/configuration.yaml`에서 어댑터를 지정합니다. ZBDongle-E는 **EmberZNet** 기반입니다.

```yaml
serial:
  adapter: ember
  port: /dev/cu.usbmodem____   # ls /dev/cu.* 로 확인
mqtt:
  server: mqtt://localhost:1883
```

ZBDongle-P(TI 기반)와 설정이 다릅니다. 잘못 쓰면 어댑터를 못 엽니다.

### 페어링

1. Zigbee2MQTT 웹 UI(`http://localhost:8080`)에서 "Permit join"을 켭니다.
2. Aqara 센서의 버튼을 5초 이상 길게 눌러 페어링 모드로 넣습니다.
3. 두 개를 각각 페어링하고 이름을 `leak_tank`, `leak_pot`으로 바꿉니다.

### 합격 기준

- 센서 두 개가 웹 UI에 보입니다.
- 젖은 휴지를 두 금속 단자에 대면 `zigbee2mqtt/leak_tank`에 `{"water_leak":true}`가 발행됩니다.
- ESP32 텔레메트리의 `leak`이 `detected`로 바뀝니다.
- Zigbee2MQTT를 끄면 5분 뒤 `leak`이 `unknown`이 되고 **급수가 거부됩니다** (fail-closed).

## Stage 8 — 안전규칙 통합 검증

**목표**: 위험 상황을 일부러 만들어 시스템이 막는지 봅니다.

⚠️ 이 Stage는 화분이 아니라 양동이에서 합니다. 일부러 실패시키는 단계입니다.

| # | 테스트 | 방법 | 기대 결과 |
|---|---|---|---|
| T1 | 빈 물통 급수 | 물통을 비우고 급수 명령 | `rejected(reservoir_empty)`, 펌프 안 돎 |
| T2 | 급수 중 물통 고갈 | 급수 중 플로트를 손으로 내림 | 1초 안에 펌프 정지, `aborted(reservoir_empty)` |
| T3 | 급수 중 누수 | 급수 중 누수센서를 적심 | 즉시 정지, `aborted(leak_detected)`, 이후 급수 잠금 |
| T4 | 잠금 해제 | 누수 제거 후 재시도 | 여전히 `rejected(locked)`. `namo/pilot/<id>/unlock` 발행 후에만 풀림 |
| T5 | 쿨다운 | 급수 직후 재요청 | `rejected(cooldown)` |
| T6 | 일일 한도 | 한도까지 반복 급수 후 재요청 | `rejected(daily_limit)` |
| T7 | TTL 만료 | `issued_at`을 과거로 조작 | 무반응. 결과 메시지도 없음 |
| T8 | 중복 명령 | 같은 `id`로 2회 발행 | 1회만 실행 |
| T9 | 급수량 상한 | `dose_ml`을 400으로 | `rejected(dose_too_large)`, 펌프 안 돎 |
| T9b | 시간 하드리밋 | `ml_per_second`를 일부러 1/10로 낮춰 300mL 요청 | 20초에서 강제 정지. 로그에 하드리밋 도달 기록 |
| T10 | WiFi 단절 | 급수 시작 직후 공유기 끔 | 펌프가 정확한 시간에 꺼짐 |
| T11 | 브로커 단절 | Mosquitto 중지 후 급수 시도 | 명령이 안 가므로 아무 일 없음. ESP32는 계속 살아 있음 |
| T12 | 리셋 안전 | 급수 중 ESP32 리셋 버튼 | 펌프 즉시 정지. 재부팅 후에도 안 돎 |
| T13 | 전원 재투입 | ESP32 USB를 10회 뽑았다 꽂기 | 펌프가 **한 번도** 돌지 않음 |

T13이 통과하지 않으면 게이트 풀다운을 다시 확인합니다.

### 합격 기준

14개 전부 통과합니다. 하나라도 실패하면 화분에 연결하지 않습니다.

## Stage 9 — 화분 세팅과 파일럿 가동

**목표**: 실제 바질 화분에 연결합니다.

### 배치

```text
[화분 A: 바질 모종]  ← 튜브 토출구 · HHCC 센서
        ↑ 튜브
    [물통 2L]  ← 펌프(잠김) · 플로트 스위치(측면)
        옆: Aqara 누수센서 #1 (바닥)
[화분 A 받침] 옆: Aqara 누수센서 #2

전자부품(ESP32·브레드보드·MOSFET): 위 전부보다 높은 선반
```

- 토출구는 물통 수면보다 **높게** 둡니다 (사이펀 방지, Stage 3 참고).
- 토출구는 줄기에 직접 닿지 않게 흙 표면을 향하게 합니다.
- HHCC는 화분 가장자리가 아니라 뿌리 근처 흙에 꽂습니다.
- 누수센서는 물통 받침과 화분 받침 **바닥**에 둡니다. 공중에 있으면 의미가 없습니다.

### 첫 주 운영

1. 첫 3일은 **자리에 있을 때만** 급수합니다. 무인 가동하지 않습니다.
2. 매 급수 후 화분 받침에 물이 얼마나 빠지는지 봅니다. 넘치면 `dose_ml`을 줄입니다.
3. HHCC 수분값과 실제 흙 상태(손가락으로 2cm 찔러보기)를 비교합니다. 센서가 실제와 다르게 나오면 꽂은 위치를 바꿉니다.
4. 바질 잎 상태를 매일 봅니다. 물이 부족하면 잎이 처지고, 급수 후 1시간이면 회복합니다. **이 반응이 센서와 별개인 급수 성공의 육안 증거입니다.**

### 씨앗 화분

화분 B에는 바질 씨앗을 뿌리고 **손으로만** 물을 줍니다. 분무기로 흙 표면을 촉촉하게 유지합니다. 발아까지 5~7일입니다.

씨앗 화분에 펌프를 연결하지 않는 이유는 발아기에 필요한 급수 방식(자주·소량·표면)이 정량 급수 검증과 정반대이기 때문입니다.

### 완료 판정

`pilot-design.md` §7의 9개 항목을 모두 만족하면 파일럿 완료입니다.

## 문제 대응

| 증상 | 먼저 볼 것 |
|---|---|
| 펌프가 아예 안 돎 | 공통 접지 → 12V 어댑터 연결 → Stage 2 재측정 |
| 펌프가 꺼지지 않음 | 즉시 12V 뽑기. MOSFET 소손 의심 (Stage 2를 건너뛴 경우 흔함) |
| 펌프가 약하게 돎 | 부분도통. Stage 2로 복귀 |
| 리셋할 때마다 펌프가 잠깐 돎 | 게이트 풀다운 누락 또는 접촉 불량 |
| 물이 안 멈추고 계속 흐름 | 사이펀. 토출구 높이 조정 |
| BLE 값이 일부만 옴 | 정상. 수 분 기다림 |
| BLE 값이 아예 안 옴 | HHCC 배터리 → Flower Care 앱 연결 상태(앱이 점유 중이면 광고가 끊길 수 있음) |
| WiFi 연결 실패 | 2.4GHz SSID인지 확인 |
| `Failed to run Python dependency check` | Python 문제가 아님. `ESP_IDF_VERSION = "v5.4.4"` 고정 (Stage 0 참고) |
| Zigbee 어댑터를 못 엶 | `adapter: ember` 확인, 포트 경로 확인, 다른 프로세스가 점유 중인지 확인 |
| 급수가 계속 거부됨 | `water/result`의 `reason` 확인. `leak_stale`이면 Zigbee2MQTT가 죽은 것 |
