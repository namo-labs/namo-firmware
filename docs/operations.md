## 1. 지금 돌고 있는 것

```text
            ┌─ 베란다 ────────────────────────┐
            │  화분 ← 튜브        HHCC 센서    │
            │  물통 + 펌프 + 플로트            │
            │  누수센서 ×2 (Zigbee)            │
            └────────┬────────────────────────┘
                     │ 12V · 신호선
            ┌─ 방 ───┴────────────────────────┐
            │  ESP32-S3  ── WiFi ──┐           │
            │  MOSFET 모듈          │          │
            └──────────────────────┼──────────┘
                                   │
   ┌─ 맥미니 ───────────────────────┼──────────────────────┐
   │  mosquitto (도커)  ←───────────┘                      │
   │  Zigbee2MQTT (LaunchAgent)  ← Sonoff 동글             │
   │  ffmpeg + python http.server ← USB 웹캠  :8090        │
   │                                                       │
   │  lima VM / k3s                                        │
   │    namo-monitor  :8080   ← MQTT 구독 · 이력 · 알림     │
   │    edge (Caddy)  :8080   ← 인증 · 경로 분기            │
   │      └ cloudflared ── Cloudflare ── kang1027.com      │
   └───────────────────────────────────────────────────────┘
```

**https://kang1027.com/namo/stats** 한 곳에서 카메라·급수·그래프·기록을
봅니다. Basic Auth 자격증명은 `~/homeserver/k8s/secrets/namo-monitor.env`.

| 경로 | 내용 |
|---|---|
| `/namo/stats` | 화면 |
| `GET /namo/api/config` | 한도·급수량 목록·알림 기준 |
| `GET /namo/api/state` | 현재 상태 + 맥락 |
| `GET /namo/api/history?hours=N` | 센서 이력 (최대 30일) |
| `GET /namo/api/events?limit=N` | 사건 기록 |
| `POST /namo/api/water` | 급수 `{"dose_ml":100}` |
| `POST /namo/api/unlock` | 잠금 해제 `{}` |
| `GET /namo/cam/stream.m3u8` | 카메라 HLS |
| `GET /namo/cam/snapshot.jpg` | 현재 프레임 (5초 갱신) |

카메라가 살아 있는지는 `/api/state`의 `camera`로 봅니다. 스트림이
받아진다는 것만으로는 알 수 없습니다(아래 §2).

### 인증

두 갈래입니다. 쓰는 쪽이 다르기 때문입니다.

- **사람(브라우저)** — Basic Auth. 한 번 저장해두면 계속 씁니다.
- **앱** — `Authorization: Bearer <토큰>`. Basic Auth 자격증명을 앱에
  심으면 계정 단위라 기기별로 끊거나 돌릴 수 없습니다.

토큰은 Caddy에서 값까지 맞춰봅니다. 카메라는 맥에서 도는 서버로 바로 가
`namo-monitor`를 거치지 않으므로, "Bearer가 붙어 있으면 통과"로 두면 아무
값이나 카메라를 볼 수 있습니다.

상태를 바꾸는 요청(`water`·`unlock`)은 `Content-Type: application/json`이
필요합니다. HTML form은 그 값을 만들 수 없어, 남의 페이지에 숨긴 폼으로
급수를 거는 길이 막힙니다.

**한도는 화면에 박아두지 않습니다.** `/api/config`에서 받아 씁니다. 장치
쪽 값을 고치면 `monitor/config_api.go`의 상수도 함께 고칩니다.

## 2. 죽었을 때

### 스스로 살아나는 것

- **Zigbee2MQTT** — LaunchAgent가 15초 안에 되살립니다.
  `launchctl list | grep zigbee2mqtt`
- **mosquitto** — 도커 `unless-stopped`
- **ESP32** — WiFi·MQTT 모두 무한 재시도
- **카메라 ffmpeg** — `cam.sh`가 세그먼트 갱신을 보고 재시작
- **브라우저 재생** — 끊기면 스스로 다시 붙음

### 손이 필요한 것

**카메라 프로세스 전체.** macOS 카메라 권한이 프로세스를 띄운 앱에
붙어서, 자동화 도구로는 띄울 수 없습니다. 맥 터미널에서 직접 실행합니다.

```bash
cd ~/project/namo-firmware && ./scripts/cam.sh
```

**웹캠이 프레임을 멈췄을 때.** `cam.sh`가 ffmpeg을 몇 번이고 다시
띄워도 화면이 돌아오지 않으면 카메라 쪽입니다. USB를 뽑았다 꽂습니다.
`cam.sh` 창이 "재시작 5회째 프레임이 돌아오지 않습니다"를 찍어 알려
줍니다. 예전 ffmpeg이 카메라를 붙잡고 있는 경우도 있습니다.

```bash
pgrep -fl ffmpeg          # cam.sh 것 말고 남아 있는 게 있는지
```

**맥미니 IP가 바뀌었을 때.** ESP32는 브로커 주소를 `cfg.toml`에 IP로
박아 두고(`192.168.219.111`) 그 주소로만 재접속합니다. 맥 IP가 바뀌면
장치는 살아 있고 센서도 받지만 MQTT에 영영 붙지 못해, 급수 명령이 닿지
않습니다. 없는 주소로 붙으려 하므로 mosquitto 로그에는 접속 시도조차
남지 않습니다.

2026-09-17 19:05에 실제로 이렇게 이틀을 멈췄습니다. 맥 Wi-Fi가 비공개
(랜덤) MAC을 쓰고 있어서, 주소가 바뀌자 공유기가 새 IP(.113)를 내줬습니다.

```bash
ipconfig getifaddr en1     # .111이어야 합니다
sudo networksetup -setmanualwithdhcprouter Wi-Fi 192.168.219.111
```

Wi-Fi 설정에서 이 네트워크의 "비공개 Wi-Fi 주소"는 끄거나 고정으로
둡니다. IP를 되돌리면 ESP32는 스스로 다시 붙습니다.

### 카메라가 죽었는지 아는 법

**재생기는 알지 못합니다.** 카메라가 얼어붙어도 플레이리스트는 200을
그대로 주고 마지막 세그먼트도 받아져서, 브라우저는 몇 시간 전 화면을
틀면서 "LIVE"를 켭니다. 실제로 여섯 시간을 그랬습니다.

그래서 `namo-monitor`가 10초마다 스트림 서버를 찔러 플레이리스트가
**방금 쓰였는지**를 봅니다. 결과는 `/api/state`의 `camera`에 실립니다.

| `status` | |
|---|---|
| `live` | 갱신 중 |
| `stalled` | 서버는 응답하지만 프레임이 멈춤 |
| `down` | 스트림 서버에 닿지 못함 (`cam.sh`가 꺼짐) |
| `unknown` | 아직 확인 전 |

화면 배지는 이 값을 재생기보다 먼저 믿습니다. 5분 넘게 돌아오지 않으면
텔레그램으로 알립니다.

## 3. 알림

흙수분이 50% 아래로 내려가거나, 누수·잠김·물통 빔·장치 무응답·카메라
멈춤이 생기면 텔레그램으로 알립니다. 풀리면 한 번 더 알립니다.

**같은 알림은 반복하지 않습니다.** 상태가 바뀌는 순간에만 보냅니다.
흙수분은 10%p 더 회복해야 해제하고(경계에서 떨리지 않게), 장치와
카메라는 5분, 게이트웨이는 10분을 기다린 뒤에 알립니다. 게이트웨이는 스스로
되살아나므로 대부분 알림 없이 지나갑니다.

봇은 portfolio와 같은 것을 씁니다. `DRY_PCT`로 기준을 조정합니다.

### 알려진 문제

**USB 대역폭.** 카메라·Zigbee 동글·저장장치가 USB 2.0 허브 하나를
나눠 씁니다. 카메라가 무압축으로 초당 6MB를 쓰면 동글이 밀려 끊깁니다.
실제로 두 번 끊겼습니다. Zigbee2MQTT가 자동 복구되므로 증상은
가벼워졌지만 원인은 그대로입니다.

반대 방향으로도 번집니다. 2026-09-17 02:55에 동글이 끊긴 1분 뒤부터
카메라가 14시간 동안 정상 출력을 내지 못했고, 전날 웹캠 USB를 뽑았을
때도 동글이 함께 끊겼습니다. 둘을 다른 버스로 나누기 전까지는 한쪽이
흔들리면 다른 쪽도 의심합니다.

재시작이 잦으면 `CAM_FPS=5`로 낮추거나, USB Storage를 빼거나, 카메라와
동글을 다른 USB 버스로 나눕니다.

**일일 급수량이 RAM에만 있습니다.** ESP32를 리셋하면 0으로 돌아가므로,
리셋을 반복하면 하루 한도를 우회할 수 있습니다. NVS에 넣어야 제대로지만
파일럿에서는 리셋할 일이 드물어 미뤘습니다.

**OTA 펌웨어 업데이트가 없습니다.** 펌웨어를 고치려면 USB를 꽂아야
합니다. 파티션 재구성과 인증이 필요해 미뤘습니다.

**카메라 자동 시작이 없습니다.** 권한 문제이며, 꺼져도 급수에는 지장이
없어 후순위입니다.

성공 여부를 판정하면 안 됩니다.
